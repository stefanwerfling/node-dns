# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**dns2ts** — a pure TypeScript DNS server and client library with zero production dependencies. Implements DNS over UDP, TCP, TLS (DoT, RFC 7858), and HTTPS (DoH, RFC 8484), client + server.

## Build & Development Commands

```bash
npm install              # Install dev dependencies
npx tsc                  # Compile TypeScript (src/ -> dist/)
npm test                 # Compile + run all tests (tsc && node dist/Test)
npm run lint             # ESLint check
npm run fix              # ESLint auto-fix
```

Example servers (run after compiling):
```bash
npm run example-server-udp    # Start UDP DNS server
npm run example-server-tcp    # Start TCP DNS server
```

## Architecture

### Module Layout (src/)

- **Lib/** — Low-level I/O and parsers: `BufferReader`/`BufferWriter` for bit-level DNS wire format parsing, `SocketReader` for TCP stream framing (accepts an optional `initialBuffer` so pre-consumed bytes can be fed in), `ZoneParser` for RFC 1035 master file parsing (tokenizer with parens/quotes/comments, `$ORIGIN`/`$TTL`/`$INCLUDE`/`@`, RFC §5.1 leading-whitespace owner-name inheritance, `$INCLUDE` accepts an optional origin override and recurses with a fresh nested state — directives in the included file do not leak back to the parent — file content is read via `fs.readFileSync` against `basePath` by default; pass `includeResolver: (filename, basePath) => string` to load from custom sources; cycles are detected and rejected, RDATA for A/AAAA/NS/CNAME/DNAME/PTR/MX/TXT/SOA/SRV/CAA plus DNSKEY/DS/SSHFP/TLSA/NAPTR/NSEC/NSEC3/RRSIG/SVCB/HTTPS — base32hex helper for NSEC3 next-hashed-owner, generic `TYPEnnn` mnemonic via RFC 3597, `_typeMnemonicToNumber` mapping for NSEC/NSEC3/RRSIG type-bit-maps, RFC 9460 §2.1 SVCB presentation form with `key=value`/quoted/`key=`-then-quoted-token glue and `keyN=` round-trip via `unknown[]`), `Random0x20` (RFC 5452 §9.2 case randomization — `scramble` flips ASCII letters via CSPRNG, `matches` is the case-sensitive verifier; wired into UDPClient/TCPClient via `use0x20: true`), `Bailiwick` (RFC 5452 §6 — `contains(zone, name)` membership predicate, `filter(packet, zone)` strips out-of-zone answer/authority/additional records while preserving questions and EDNS OPT), `Dnssec` (RFC 4034/4035 stateless verifier — `verifyRrsig(owner, rrset, rrsig, dnskey, {now?, skipValidityWindow?})` builds the canonical signing input per §3.1.8.1 then dispatches to Node `crypto.verify` for algorithms 8 RSA/SHA-256, 10 RSA/SHA-512, 13 ECDSA P-256, 14 ECDSA P-384, 15 Ed25519; ECDSA uses `dsaEncoding: 'ieee-p1363'` so DNS raw-r||s round-trips without DER conversion; `computeKeyTag` per RFC 4034 Appendix B; `computeDsDigest`/`verifyDs` for digest types 1/2/4. Canonical RDATA covers wire-already-canonical types (A/AAAA/DS/DNSKEY/TXT/SPF/CAA/TLSA/SSHFP/NSEC3) plus all embedded-name types: NS/CNAME/DNAME/PTR/MX, SOA, SRV, NAPTR (replacement only — char-strings keep case per §6.2 step 2), NSEC, and RRSIG-of-RRSIG. Multi-name types are canonicalized by cloning the record with lowercased name fields and calling the type's existing `encode` (which already builds RDATA in a fresh writer, so no compression leaks in). RFC 4034 §3.1.3 wildcard label-count reconstruction is in `_reconstructSignedOwner`: when `rrsig.labels < owner_label_count` the validator infers `*.<trailing labels>` as the signed owner; `rrsig.labels > owner_label_count` is rejected as malformed per RFC 4035 §5.3.1. For negative answers, the building blocks are exposed: `canonicalNameCompare(a, b)` (RFC 4034 §6.1 right-to-left label-by-label), `nsecCovers(owner, next, query)` (handles end-of-zone wrap-around), `nsec3Hash(name, saltHex, iterations, algorithm=1)` (RFC 5155 §5 SHA-1 with iterations+1 calls — RFC 9276 forbids non-1 algorithms), `nsec3CoversHash(owner, next, query)` (Buffer-compare wrap-around), `base32hexEncode(buf)` (RFC 4648 §7 unpadded). The end-to-end "prove NXDOMAIN with closest-encloser + next-closer + wildcard" composition is left to the caller — it depends on the message-shape conventions a recursive resolver provides. For the authoritative side, `signRrset(owner, rrset, dnskey, privateKey, options)` produces an RRSIG that verifies through `verifyRrsig` by construction — same `buildSigningInput` is used on both sides. `publicKeyToDnskey(publicKey, algorithm)` is the inverse of the verifier's per-algorithm public-key parsers (RFC 3110 RSA, raw-point ECDSA, raw-32-byte Ed25519). `signZone(zone, {ksk, zsk, inception, expiration, dnskeyTtl?, nsec?})` is the convenience wrapper: groups records by lowercased (name, type), synthesizes the DNSKEY RRset at the apex from the provided keys, signs the DNSKEY RRset with the KSK and every other RRset with the ZSK, returns `{records, rrsigs}`. Passing `ksk === zsk` collapses to the CSK case. Wildcard owners sign correctly via `signRrset`'s default — leading `*` is excluded from the labels count per RFC 4034 §3.1.3. With `nsec: true`, an NSEC chain (RFC 4034 §4) is generated covering every owner name in the zone — sorted canonically with `canonicalNameCompare`, wrapping back to the apex, with each name's type bit map listing the types actually present plus RRSIG and NSEC. With `nsec3: {salt?, iterations?, optOut?}` (RFC 5155 / RFC 9276 — defaults: salt empty, iterations 0, opt-out off), the chain instead uses hashed owner names (base32hex(SHA-1(name||salt) iterated)), sorted by hash bytes, with an NSEC3PARAM RR at the apex. NSEC3PARAM is type 51, registered in the type registry. The `nsec` and `nsec3` options are mutually exclusive. Out of scope: chain-of-trust traversal from a trust anchor to the answer's signer).
- **Packet/** — DNS packet model (RFC 1035): header, question, resource record encoding/decoding, domain name compression, class/type enums. `Packet/Zone.ts` is the in-memory zone representation (origin + records + `soa()`, `recordsOfType()`, `fromZoneFile()`, `toAxfrPackets(query)` for RFC 5936 §2.2 single-message AXFR, and `toIxfrPackets(query, {history?})` for RFC 1995 IXFR — picks no-change / incremental / AXFR-fallback automatically based on the client's serial in the AUTHORITY section and the supplied `ZoneChangeSet[]` history). `Packet/Update.ts` ships `UpdateBuilder` (fluent API for RFC 2136 messages — five prerequisite kinds, four update kinds), `Update.parse/classify*` for the server side, and `Update.applyToZone` as a reference engine that mutates a `Zone` in place and returns the matching `UpdateRcode`. `PacketResource.rdlength` is captured during decode so prerequisite/update markers (rdlength=0) can be distinguished from records that happen to encode small payloads — required because the registered type decoder for e.g. type=A would otherwise produce an `A('')` instance from a 0-length RDATA, which `instanceof UnknownPacketType` doesn't catch.
- **Packet/Types/** — 27 record type implementations (A, AAAA, MX, NS, CNAME, DNAME, PTR, SRV, SOA, TXT, SPF, CAA, EDNS, DNSKEY, DS, CDS, CDNSKEY, NAPTR, NSEC, NSEC3, NSEC3PARAM, RRSIG, SSHFP, TLSA, SVCB, HTTPS, TSIG), each extending abstract `PacketType`. HTTPS is a thin subclass of SVCB — same RFC 9460 wire format, different type code. CDS / CDNSKEY (RFC 7344) follow the same pattern: subclasses of DS / DNSKEY whose `decode` rebrands the parent's instance — wire format identical, type codes 59 / 60. Used by RFC 8078 child-side automation to push DS changes to the parent. RRSIG has a full encode/decode round-trip; the rdata writer is fresh per RFC 6840 (no compression for DNSSEC RR types) and presentation dates accept either `YYYYMMDDHHMMSS` (UTC) or unsigned-decimal seconds. Unknown types are handled gracefully via `UnknownPacketType`. EDNS dispatches to per-option classes (`EdnsECS`, `EdnsCookie`, `EdnsPadding`, `EdnsNsid`, `EdnsKeepalive`, `EdnsExtendedError`) via the `EdnsOption` interface (each provides `encode(writer)` + static `decode`).
- **Packet/Types/EdnsCookie.ts** — DNS Cookies (RFC 7873) wire format plus RFC 9018-style server-cookie helpers: `generateClientCookie()`, `computeServerCookie(clientCookie, clientIp, secret, ts?)` returns 24 bytes (1B version + 3B reserved + 4B unix timestamp + 16B truncated HMAC-SHA256), `verifyServerCookie(...)` does a `crypto.timingSafeEqual` against a recomputed cookie and supports an optional `maxAgeSeconds` window.
- **Packet/Tsig.ts, Packet/TsigKey.ts** — TSIG signing + verification (RFC 8945). `TsigKey` holds the shared secret; `Tsig.sign(packet, key)` patches ARCOUNT, computes HMAC (built-in `crypto`) and appends the TSIG RR; `Tsig.verify(packet, receivedBytes, key)` relies on `PacketResource.byteStart` to slice the original wire bytes and does a constant-time MAC check plus fudge-window validation.
- **Server/** — `UDPServer`, `TCPServer`, `TLSServer` (DoT, RFC 7858), `DohServer` (individual protocol servers) and `DnsServer` (combined multi-protocol server). Shared config in `ServerOptions` (with `udp`/`tcp`/`tls`/`doh` blocks). `TLSServer` extends `TCPServer` by overriding two protected hooks (`_loadHooks` reads `options.tls.preRequest`/`preConnection`; `_createInternalServer` returns `tls.createServer(options.tls.options, listener)`); the rest of the framing/handler logic is inherited. Two hook interfaces: `ServerPreRequest<TClient>` (per message) and `ServerPreConnection<TClient>` (per TCP/TLS connection). The `send` callback accepts `Packet | Packet[]`; on TCP/TLS an array writes all packets as length-prefixed frames before closing (used by AXFR), on UDP only the first element is sent.
- **Server/ProxyProtocol/** — PROXY protocol v1 (text) and v2 (binary) implementations. `ProxyProtocolV1`/`V2` implement `ServerPreRequest<dgram.RemoteInfo>` for UDP; `ProxyProtocolV1Tcp`/`V2Tcp` implement `ServerPreConnection<net.Socket>` and override `remoteAddress`/`remotePort` via `Object.defineProperty`. `ProxyProtocolTcpReader` is the shared incremental socket-reading helper.
- **Client/** — `UDPClient`, `TCPClient` (TCP + TLS), `DohClient` (http/https/h2), `GoogleClient` (Google JSON API), `AxfrClient` (RFC 5936 zone transfer over TCP/TLS — reassembles multi-message replies, terminates on the closing SOA), `IxfrClient` (RFC 1995 incremental transfer — classifies the response into `noChange | incremental | fullAxfr`), `NotifyClient` (RFC 1996 zone-change notification, UDP/TCP/TLS, returns the secondary's ack packet), `UpdateClient` (RFC 2136 dynamic update; takes an `UpdateBuilder` or pre-built `Packet`). All expose a static `request()` method returning a resolver function.
- **DNS.ts** — High-level resolver that tries multiple nameservers in parallel, supports all protocol types.
- **Test/** — Test framework and themed test modules (272 tests). `index.ts` is a thin barrel that imports the modules in order; tests live in `buffers.ts`, `name.ts`, `packet.ts`, `edns.ts`, `recordTypes.ts`, `proxyProtocol.ts`, `tsig.ts`, `zoneParser.ts`, `axfr.ts`, `ixfr.ts`, `notify.ts`, `update.ts`, `security.ts`, `dnssec.ts`, `serverDoh.ts`, `serverIntegration.ts`, `serverTls.ts`. Shared fixtures (`response` buffer, HTTP `get` helper, bundled TLS cert/key, `dotQuery` helper) live in `helpers.ts`. The `zoneParser.ts` module ships a `dedent` helper for indented multi-line zone literals — RFC 1035 leading-whitespace semantics conflict with template-literal aesthetics, so test inputs are dedented before parsing. The `dnssec.ts` module generates synthetic key pairs at test time (RSA, ECDSA P-256/P-384, Ed25519), signs an RRset with `crypto.sign`, then verifies through the public API — covers algorithm dispatch, canonical RDATA sorting, embedded-name lowercasing, validity-window enforcement, and tampering rejection; passes a fixed `now` so the inception/expiration check stays deterministic across CI clock drift.
- **index.ts** — Barrel re-export of all public API

### Key Patterns

- **PacketTypeRegistry** is a singleton that maps DNS record type numbers to `PacketType` subclass instances. All 23 types are registered at first access.
- **PacketResource.byteStart** is populated by `PacketResource.decode` with the byte offset of the record in the source buffer. Required by TSIG verification to reconstruct the exact MAC input without re-serializing (which could produce different bytes if DNS compression differs).
- **Buffer operations** are bit-precise but byte-backed. `BufferReader`/`BufferWriter` keep a `Buffer` / `number[]` of bytes plus a bit-offset counter. `read`/`write` take a hot path for byte-aligned 8/16/32-bit fields (Node-native `readUInt*BE` / direct byte stores) and a bit-shift loop for sub-byte fields (1-bit flags and 4-bit OPCODE/RCODE in the 12-byte header). The previous bit-array representation was ~150× slower on encode and ~18× slower on decode for typical packets — when touching this code, preserve the bit-precise semantics (callers like `PacketName.encode` register name-compression offsets via `getByteOffset()`, which still floors the bit length to a byte). `BufferWriter.writeBuffer()` accepts a `Buffer` (byte append) or another `BufferWriter` (bytes + remaining bits).
- **TCP framing** uses 2-byte length prefix per message, handled by `SocketReader`.
- **Servers** emit `request` events with parsed `Packet` objects and a send callback. `DnsServer` combines multiple protocol servers and forwards all events.
- **Pre-hooks** — `preRequest` (per-message) and `preConnection` (TCP/TLS-only, per-connection) are configured via `ServerOptions.udp|tcp|tls|doh`. Both can return a `client` override that the server emits in place of the original. For TCP/TLS `preConnection`, the server passes the returned `initialBuffer` (any bytes read past the PROXY header) to `SocketReader.readStream` so DNS framing continues seamlessly. Responses always go back to the true transport peer; only the emitted client reference is swapped.
- **Clients** follow a factory pattern: `XClient.request(options)` returns an async resolver function `(name, type, cls, options?) => Promise<Packet>`. `UDPClient` automatically retries via `TCPClient` when the response header has the TC (truncation) bit set (RFC 7766 §8); opt out via `tcpFallback: false`, override target with `tcpFallbackPort`. `AxfrClient.request(options)` returns `(zoneName) => Promise<{soa, records}>` and uses TCP/TLS only.
- **`Packet.createResponseFromRequest`** shares the `header` object reference with the request — fine for the common single-response flow but a footgun when you build multiple responses from the same request and want to mutate per-response header fields (e.g. distinct IDs). For multi-packet responses (AXFR-style), build fresh `new Packet()` instances and only copy what's needed.
